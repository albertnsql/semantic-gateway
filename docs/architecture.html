SemanticGateway

A natural-language analytics gateway over a governed dbt semantic layer. The organising rule, and the reason every component sits where it does: the LLM never writes SQL.

It extracts intent — metric, dimensions, time range, filters — and MetricFlow compiles the SQL from a governed manifest.

01 The governance boundary

Everything else in this document is downstream of one decision. A model that emits SQL can invent a column, a join, or a filter, and the result is a confident wrong number that nothing catches. So the model's output is a typed QueryIntent — never a string of SQL.

Read-only is enforced in SQL, not by the connection.

dbt-duckdb hardcodes read_only=False, and DuckDB refuses a second connection with a different config in one process — and this process hosts the in-process MetricFlow engine. So the pool connects read-write and assert_read_only() rejects anything that is not a single WITH/SELECT before execution. A read-only dbt target cannot work here.

02 Three pieces, one of them deployed

Only gateway/ ships to production; the other two are a client and a compiler input. A fourth piece, backend/, held the eval harness and the prompt-grounding skill files until 2026-09-10 — it was folded into gateway/, because the deployed service was reading those skills from outside its own root directory at runtime.

03 The request pipeline

Thirteen ordered stages, four possible branches, three caches that can short-circuit the whole thing. Stage numbers below match the # ── Stage N comments in api/routes/query.py.

  1. 0

    Raw-question cachecache

    Keyed on the normalised question plus a hash of conversation history, whether dashboard context was supplied, and max_rows. Exists because the L2 cache is intent-keyed and therefore sits after the first LLM call. Measured on one repeated question: 11,662 ms → 9.8 ms → 7.2 ms.

  2. 1

    IntentExtractorLLM #1

    One call both classifies (metric_query / schema_question / diagnostic_query / out_of_scope) and extracts the intent. There is deliberately no separate classifier round-trip.

  3. 1.25

    Route on query_type

    Branches on the field the extraction call already returned.

  4. 1.3

    Diagnostic path

    The “why did this move” branch. A LangGraph agent, zero LLM calls of its own — see section 06.

  5. 1.5

    Clarification and time-grain validationcan exit

    Rejects an under-specified or wrong-grain question before it costs a compile.

  6. 2

    Intent-keyed result cache (L2)cache

    SHA256(metric + dimensions + time_range + filters). A hit returns immediately, skipping validation, SQL generation and the warehouse. Two phrasings of one question share an intent but not a raw key.

  7. 3

    SemanticValidator

    Rejects a metric×dimension combination that is not certified. Certification is an assertion, so a separate audit pushes all 267 pairs through the real compiler and checks each returns more than one distinct bucket.

  8. 4

    Dry runcan exit

    Returns the plan and the SQL without touching the warehouse.

  9. 5

    SQL generation

    MetricFlow first, on every query, then three fallback rungs — section 05.

  10. 6

    Warehouse execution

    DuckDBPool.execute(), every statement through assert_read_only(). Column names are uppercased so the downstream response shaping — written against Snowflake's DictCursor — did not have to change.

  11. 7–8

    Lineage resolution and response assembly

    Attaches grain and the raw → stg → int → mart → metric chain, read straight out of the dbt manifest.

  12. 8b

    Narrative summaryLLM #2

    Writes the prose from the result rows. It sees values, not semantics — so it will narrate whatever metric Stage 1 picked, and a wrong metric with right numbers still reads as a confident answer.

Where the latency actually is

MetricFlow compiles in 60–96 ms and a local DuckDB query is milliseconds. The two LLM calls are ~1–2 s each, so they are roughly 90% of a 2.9–5.2 s round trip. Retrieval tuning touches neither.

04 Two read paths to the same warehouse

The dashboard does not use any of the above. It is a separate, deliberate path — and the reason the same business concept can be defined twice.

The maintenance rule this creates

When you change a metric definition, check _WIDGET_SQL for a widget computing the same thing, and vice versa. churn_rate was redefined once specifically so its formula would match the widget.

A second trap: an empty widget result is not an error to the frontend — it is silently replaced with mock data and labelled “Estimated”. Anything wearing that label is worth checking against the warehouse before believing it.

05 SQL generation: four rungs

MetricFlow runs first on every query, because the semantic layer is the source of truth and compiling from it is cheaper than the round trip it feeds. The rungs below it exist for engine unavailability — not for retrying a query the compiler has already rejected.

Three normalisations run before any of it

The validator certifies dimensions by their bare name; MetricFlow resolves them by their qualified name. Nothing reconciled the two, so three guards now sit at the top of generation — before the post-filter split, the cache key, or the outer predicate read the names.

Guards between validation and the compiler.
GuardFixes
correct_dimension_entity()An entity prefix the model invented that is unreachable from the metric. Narrow by design — a deliberate choice between two reachable entities is never second-guessed.
require_metric_time()An offset metric cannot resolve without metric_time in the group-by. Grain is read from the offset window, not hard-coded.
is_deterministic_mf_error()Stops the pointless subprocess retry. A query-resolution error is deterministic; retrying it burned 24 s reaching a byte-identical verdict.

06 The diagnostic path

A “why did this move” question does not narrate one result set — it gathers evidence. A LangGraph agent plans probes, Python computes the attribution, and MetricFlow still writes every line of SQL.

What licenses a causal claim

The narrative path is forbidden causal language because a model handed three numbers will invent a reason. This path may say “because” only because arithmetic computed the attribution first — and every claim ships with the probe ids behind it, so a reader can check it rather than trust it.

Effect-size gates. Each without the other misfires on real data.
GateThresholdPrevents
Lift≥ 1.25×Naming the biggest bucket, which carries the most movement almost by definition.
Share of gap≥ 25%Reporting a segment holding a fourteenth of the movement as its driver.
Reconciliation5% tol.Attributing a metric that does not sum across segments. A sign disagreement fails outright.

Two modules the causal claims rest on — analysis.py and windows.py — are import-pure, and a test runs a subprocess import that fails if config, duckdb, openai, metricflow or dbt appear in sys.modules. One convenience import would cost that.

07 LangGraph, and why it is quarantined

One module imports it. core/diagnostics/graph.py is the only file in the package that knows LangGraph exists — every other module is a plain function over plain dataclasses. That isolation buys two things: the analysis engine is testable with langgraph absent, and if a 200-line asyncio orchestrator later turns out to be enough, this is a one-file replacement rather than a rewrite.

It is expensive, so it is built lazily and memoised

The import alone measures 10.7 s and +68.6 MB RSS, against ~251 MB already resident on a 512 MB instance. So build_diagnostic_agent() is never called at import time. get_diagnostic_agent() caches both success and failure — matching the warm MetricFlow engine — so a deployment where LangGraph cannot import does not re-pay the 10.7 s on every diagnostic question, and a threading.Lock makes the build happen once even when several anyio worker threads arrive together.

Two channels, and they are not the same channel

This is the part worth having a picture of. State flows through the nodes and is merged by per-key rules; services are injected sideways per invocation and never enter state at all.

The annotation trap that costs an afternoon

LangGraph decides whether to inject the config by matching the node's raw annotation string — not by resolving the type. Get it wrong and the node receives None, every service lookup returns None, and it surfaces from inside the graph as 'NoneType' object has no attribute 'validate', which reads like a wiring bug and is a typing one.

The third row is the instructive one: typing.get_type_hints() resolves it correctly and it compares equal to the fourth, so the annotation is not the problem — the string match is. LangGraph's own warning names RunnableConfig | None as acceptable and then rejects it, so the message cannot be trusted. Keep the bare form; the = None default stays so nodes remain directly callable in tests.

The same import block aliases RunnableConfig to dict when langchain_core is absent, which is what keeps this module importable — and its nodes unit-testable — with LangGraph not installed at all.

Why the loop decision is a function, not a node

should_reflect must not write state, and keeping it pure means the routing decision is testable without a graph or a warehouse. It returns the next node name and nothing else. Its gates run in this order, and the last one is the termination guarantee that does not depend on the budget being configured correctly:

The four reflect gates, and what each prevents.
GatePrevents
Nothing to explainSpending the full budget on a gap of ~0. No axis can decompose a movement that is not there.
A driver was foundLengthening an answer that already has its cause. Tested with leading_driver(), so a merely large bucket does not stop the loop.
Budget spentRounds, probes and the deadline together — 3 / 40 / 25 s.
No axes leftRe-analysing identical findings forever. Each round consumes axes from a finite list and the planner excludes what was already asked.
Two gates that look right and are not

Gating on verdict in ("explains", "partial") is the obvious reading of “something explains it” and it means the loop can never fire: all nine snapshot scenarios return partial on every axis. partial means “this axis leads a bit”, not “this is the cause”.

Gating on is_broad_based() is also wrong here, though it is right for deciding what to report: it requires at least two axes, so a diagnosis that examined one axis and found nothing — precisely the one most worth extending — would stop.

Rounds are idempotent by construction

execute_probes_node skips any probe whose label already carries an ok finding, so a reflect round costs only its new axes rather than re-running the whole cumulative plan. It also seeds the tool with the findings gathered so far, because citation ids are derived from that list — starting from empty would mint a second F1 and the answer's [F1] would point at two different probes.

One measurement detail sits here too: the deadline clock starts after the first probe, because that probe can pay the 43 s cold MetricFlow engine build. That is one-off infrastructure warm-up, not diagnosis work, and timing it defeated the deadline it was meant to enforce.

One tool, and it is the governed path

The agent has exactly one way to reach data: run_governed_query(), which emits a QueryIntent into the same SemanticValidator → SQLGenerator → pool chain the NL pipeline uses. Every probe therefore inherits certification, filter coercion, assert_read_only() and both cache layers — a probe can even hit an L2 entry a user query populated, and vice versa.

Failure handling splits deliberately. An execution error comes back as a Finding with error set, so one dead probe costs its own evidence slot and not the whole diagnosis. A governance rejection raises, because that means the agent asked for something uncertified — a bug in the plan, not a data problem.

Zero LLM calls, end to end.

Planning needs the metric (intent extraction already supplied it), the dimensions (driver_graph.yml orders them) and the windows (windows.py builds them) — none of which needs a model. Analysis is arithmetic by construction, and each hypothesis already carries a plainly-worded statement. So a diagnosis is reproducible, and it does not compete with chat traffic for provider quota. A later prose pass can sit on top, but the numbers and the strength claims still originate here — which is what keeps the citation check meaningful rather than decorative.

08 The semantic layer

Four dbt layers, lineage in one direction only. The gateway reads target/manifest.json directly, which is why dbt compile has to be re-run after any model change or lineage resolves stale.

Three layers must agree before a dimension is answerable

The mart has to select the column, the semantic model has to expose it or reach it through an entity, and the registry has to certify it. They have been out of step in both directions — a dimension MetricFlow could serve being rejected as uncertified, and a metric certifying a dimension MetricFlow refuses. An audit tool is what tells the two apart; reasoning about the layers is not reliable.

A third axis exists beyond “certified” and “compiles”: populated. A dimension can pass both and still return a single null bucket, which once produced a broken join reported as a business finding with no error anywhere. Current state: 267 pairs certified, 267 compile, 266 populated, and the one exception is correct by construction.

The trap that will bite again

The primary is a reasoning model. Its thinking tokens bill against max_tokens and appear nowhere in the usage payload, so the symptom of an over-tight cap is not a truncated answer but an empty one — an unrecoverable error on the intent path and silently missing prose on the narrative path.

reasoning_effort="none" is the fix, and it lives in one per-provider settings helper rather than at the call sites, because providers reject unknown parameters and one of them 400s on a neighbouring field.

Retrieval does not run

The embedding index is never consulted, for two independent reasons, and both failures are caught and logged as warnings before degrading silently to injecting the full metric list. That is the right outcome regardless: top-k retrieval makes the candidate set depend on phrasing, which is what made metric choice unstable in the first place. With 20 metrics the whole list fits comfortably in the prompt.

The five failing dbt tests are a deliberate decision

All five are content_id relationship tests. The synthetic source CSVs were generated across independent runs, so the content id spaces are disjoint — the joins fail in the raw data itself, which is why the warehouse engine is irrelevant to them.
